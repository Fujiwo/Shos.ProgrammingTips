## 2. 記事の構成

`執筆プロファイル.md` の型A(これまでの書き方・課題 → 新しい機能 → 解決する点)に沿う。関数ポインター・関数オブジェクトとの比較は、「これまでの書き方と課題」と「比較のまとめ」の2か所に分けて置く。前者で課題を示し、後者でラムダ式を加えた3者を表で整理する。

| 節 | 内容 | 4点との対応 |
|---|---|---|
| 導入 | 「ラムダ式を紹介します」で始め、利点(処理を、使う場所にその場で書ける。周りの変数も取り込める)を短く述べる。前提(1-2) | |
| これまでの書き方と課題 | 「しきい値以上の得点を数える」処理を `std::count_if` に渡す。関数ポインターでは、しきい値を実行時に変えられない(グローバル変数に頼ることになる)。関数オブジェクトなら状態を持てるが、使う場所から離れた所にクラスを定義する必要がある | |
| ラムダ式とは | 名前のない関数オブジェクトを、式としてその場で作る機能。コンパイラーは、`operator()` を持つ名前のないクラス(クロージャー型)を作り、そのオブジェクト(クロージャーオブジェクト)を生成する。例 2 の関数オブジェクトとほぼ同じものを、コンパイラーが書いてくれる | 意味 |
| ラムダ式の書き方 | `[キャプチャー](引数) -> 戻り値の型 { 本体 }` の各部分。C++11 では、本体に `return 式;` が一つだけある場合に戻り値の型を省略できる。それ以外の例では戻り値の型を明示する。キャプチャーの書き方を表で示す(`[]`・`[x]`・`[&x]`・`[=]`・`[&]`・`[this]`)。値のキャプチャーは作った時点のコピー、参照のキャプチャーは元の変数を見る。`[this]` はオブジェクトではなく `this` ポインターを取り込む。メンバー関数内では、`[=]`・`[&]` もメンバーの使用に伴って `this` を暗黙に取り込む | 書き方 |
| ラムダ式を使うメリット | 処理を使う場所に書けるので、読み手が定義を探しに行かずに済む。周りの変数をキャプチャーで取り込めるので、状態を渡すためのクラスが要らない。関数オブジェクトと同じく型が一つに決まるので、コンパイラーがインライン展開しやすい | メリット |
| 関数ポインター・関数オブジェクトとの比較 | 3者を表で比べる(下の表)。キャプチャーしないラムダ式は関数ポインターに変換できるので、C の API(コールバック)にも渡せる | |
| 使うときの注意点 | 参照でキャプチャーした変数より、ラムダ式が長生きすると、無効な参照が残る。`[=]`・`[&]` の一括キャプチャーは、何を取り込んだかが読み手に見えにくい。長くなった処理は、名前を付けた関数に切り出す | |
| まとめ | 3点程度の箇条書き。C++14 以降の拡張(ジェネリックラムダ、初期化キャプチャーなど)は事実だけを1文で書き、予告はしない | |

### 2-1. 比較の表(案)

| 観点 | 関数ポインター | 関数オブジェクト | ラムダ式 |
|---|---|---|---|
| 状態(しきい値など)を持てるか | 持てない(グローバル変数などに頼る) | メンバー変数で持てる | キャプチャーで持てる |
| 定義を書く場所 | 名前空間スコープの関数 | クラスの定義が要る | 使う場所に式として書ける |
| インライン展開 | 呼び出し先がポインター経由になり、されにくい | されやすい | されやすい |
| 型名を書けるか | 書ける (`bool (*)(int)`) | 書ける(クラス名) | 書けない。`auto`、テンプレート、`std::function` で受ける |
| C の API に渡せるか | API が要求する関数ポインター型に合えば渡せる | 渡せない | キャプチャーせず、API が要求する関数ポインター型に合えば渡せる |

- インライン展開の行は、断定の根拠が要る。最適化の挙動はコンパイラー任せなので、「されやすい/されにくい」の傾向として書き、出典を添える(候補は 6節)。出典を確かめられない場合は、この行を表から外す(9節)。ベンチマークは載せない(環境で数字がぶれ、要点がぼやけるため)。
- `std::function` は、ラムダ式を変数やメンバーに保持する手段として名前を出すだけにする。

## 3. コード例

すべて `CPlusplus11Lambda/main.cpp` に、例ごとの関数として置き、`main` から順に呼ぶ。記事には各関数の本体(と、例 1・例 2 では関数・クラスの定義)を埋め込む。

題材は「得点の一覧 (`std::vector<int>`) から、しきい値以上の得点を数える」で統一する。データの準備は `MakeScores` に分け、記事では省く。

| 例 | キャプション案 | 内容 |
|---|---|---|
| 例 1. | 「関数ポインターで条件を渡す」 | `bool IsPassing(int score) { return score >= 60; }` を `std::count_if` に渡す。しきい値は関数の中に固定され、実行時に変えられない |
| 例 2. | 「関数オブジェクトで、しきい値を持たせる」 | `class AtLeast`(コンストラクターでしきい値を受け、`operator()` で比べる)を `std::count_if` に渡す。しきい値は変えられるが、クラスの定義が使う場所から離れる |
| 例 3. | 「ラムダ式で、しきい値をキャプチャーする」 | `[threshold](int score) { return score >= threshold; }` を `std::count_if` に渡す。例 2 と同じ結果を、使う場所に書ける |
| 例 4. | 「値のキャプチャーは、作った時点の値を使う」 | `[threshold]` と `[&threshold]` の二つのラムダ式を `auto` で受け、作ったあとで `threshold` を変えてから呼ぶ。値のキャプチャーは古い値のまま、参照のキャプチャーは新しい値を使うことを出力で示す |
| 例 5. | 「参照のキャプチャーで、結果を外の変数に集める」 | `std::for_each` と `[&total, &count]` で、合計と件数を外の変数に集める。参照でキャプチャーする典型的な使い方 |
| 例 6. | 「キャプチャーしないラムダ式は、関数ポインターに変換できる」 | `std::qsort` 用に `int (*)(const void*, const void*)` 型の比較関数ポインターを用意し、同じシグネチャーのキャプチャーしないラムダ式を代入して渡す。`bool (*)(int)` とは別の関数ポインター型であることを明示する |

- 例 1〜3 が、この記事の要。同じ題材を3通りで書き、ラムダ式が関数オブジェクトの書きやすい形であることを見せる。
- 例 3 で「ラムダ式とは」の説明につなげる。クロージャー型を手で書くと例 2 とほぼ同じになることを、地の文で示す(コード例にはしない)。
- 注意点では、ローカル変数を参照でキャプチャーしたラムダ式を関数から返すと、変数の寿命が尽きた後に参照を使うことになり未定義動作になる、と地の文で説明する。`this` もポインターのキャプチャーであり、ラムダ式がオブジェクトより長生きすると問題になることを添える。`[=]` でメンバーを使うと `this` が暗黙に取り込まれる点にも触れる。いずれも危険な動作をするコード例にはしない(9節)。
- 例 6 は載せる。記事が長くなりすぎた場合だけ、比較の表と `※` の注記に縮める(9節)。
- 範囲 for 文は使ってよい(C++11)。ただし、ラムダ式の話に集中させるため、`std::count_if`・`std::for_each` などのアルゴリズムで書く。
- 出力は英語、コメントは日本語にする(`CPlusplus11-auto.md` と同じ理由)。
- 本文に載せる出力は、実行結果と一致させる。

## 4. 扱わないこと

この記事は一つの機能に絞るため、次は扱わない。必要なら `※` の注記で触れる程度にする。

- ジェネリックラムダ (`[](auto x)`) と初期化キャプチャー (`[p = std::move(ptr)]`)。C++14 の機能
- `constexpr` ラムダ (C++17)、`[*this]` (C++17)、テンプレートラムダ (C++20)
- `mutable` の詳細。値でキャプチャーした変数を書き換えたいときに使う、と注記で触れる程度にする
- `std::function` の仕組みと性能(型消去、ヒープ確保)
- `std::bind` との比較
- `[this]` の詳しい使い方。キャプチャーの表に載せるだけにする

## 9. 決定事項

著者の確認を得て、次のとおり決めた(2026-10-24)。

- タイトルは案1「C++11 のラムダ式: 関数オブジェクトのクラスを書かずに、処理をその場で渡す」とする。

- インライン展開の比較は、出典を添えて表に入れる。出典を確かめられない場合は、表から外す。
