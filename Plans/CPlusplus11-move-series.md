## 4. 共通の前提

既存の C++11 の記事(`CPlusplus11-auto.md`、`CPlusplus11-lambda.md`)とそろえ、各記事の冒頭に次を書く。

- 言語: C++11 以降
- 開発環境: Visual Studio 2026 (MSVC v145)。MSVC には `/std:c++11` がないため、`/std:c++14` でビルドした
- 確認: g++ 13.3 の `-std=c++11` でもビルド・実行し、C++11 の範囲に収まっていることを確かめた

サンプルは次のとおりにする。

- プロジェクトの設定は `CPlusplus11Lambda.vcxproj` を基にし、`LanguageStandard` を `stdcpp14` にする(全構成)。
- C++11 の範囲に収まっていることを、g++ の `-std=c++11 -pedantic-errors -Wall -Wextra` で確かめる。`Tools/build_cpp_samples.py` (CI) は `stdcpp14` を `-std=c++14` に読み替えるので、C++11 の範囲の確認は、この手作業のビルドだけで行う。
- 警告を出さないコードにする。g++ 13 の `-Wall` には `-Wself-move`(自己ムーブ代入)や `-Wpessimizing-move`(`return std::move(local);`)が含まれるので、これらをサンプルで呼ばない。
- 出力は英語、コード内のコメントは日本語にする。
- コピーとムーブの回数や処理時間など、実装や環境で変わる値を出力しない。特に次に注意する。
  - `std::string` は、短い文字列をオブジェクトの中に持つ実装 (SSO) が多いため、ムーブしてもバッファーを引き継がないことがある。バッファーの引き継ぎを見せるときは、`std::vector` を使う。
  - `std::vector` の容量の増え方は、実装で異なる。`reserve(n)` が保証するのは容量が `n` 以上になることであり、`n` と等しくなるとは限らない。要素の追加中の再確保を避けるには、必要な個数を先に `reserve` する。再確保そのものを見せる記事 3 では、要素を準備した後に `reserve(v.capacity() + 1)` を呼び、その呼び出し中の出力だけを比較する。
  - 標準ライブラリの型は、別途規定がない限り、ムーブ後も有効だが値は未規定となる。自作の型では、ムーブ後の状態をその型の契約として定める。サンプルでは、ムーブ元の値を出力しない。

説明では、次の区別を4本でそろえる。

- 右辺値には、一時オブジェクトだけでなく、`std::move` で右辺値として扱った変数も含まれる。右辺値参照で受け取っても、ほかから参照されないことは保証されない。
- `std::move` と `std::forward` はキャストであり、実際にムーブするかどうかは、渡した先の処理による。
- `std::move` は `const` を取り除かない。一般的な `T(T&&)` では `const T&&` を受け取れず、コピー可能ならコピーされ、コピーできなければコンパイルエラーになることがある。
- ムーブの計算量は型と操作による。記事 2 の定数時間という説明は、`std::vector` のアロケーターを別途指定しないムーブ構築に限定する。
- 記事 3 の `noexcept` の比較には、コピー可能な型を使う。コピーできない型では、例外を送出する可能性のあるムーブが使われる場合もある。
- 「値で返せる」ことを、ムーブだけの効果として書かない。C++03 でも、戻り値の最適化 (RVO・NRVO) でコピーが省かれることは多かった。ただし省略は保証されず、省略されないとき(複数のローカル変数を条件で返し分けるなど)は要素がすべてコピーされた。C++11 で変わったのは、コピーが省略されないときも、ローカル変数を `return` するとムーブになる点である。メリットは「コピーの省略に頼らなくても、値で返したときに要素がコピーされない」のように書く。

## 6. 執筆の順序と手順

記事 1 → 2 → 3 → 4 の順に書く。`std::move` の正体と、記事 3 のムーブコンストラクターの引数 (`T&&`) は、記事 1 の右辺値参照が前提になる。記事 4 の転送参照は、`T&&` の形なのに右辺値参照ではないので、記事 1〜3 の後に置く。

記事ごとに次の手順を繰り返す。既存の記事の計画書(`Plans/CPlusplus11-lambda.md` 8節)と同じ手順である。

1. 記事ごとの計画書の確認
2. サンプルコードの実装(`sustainable-code-jp`)と、g++ での動作確認
3. Visual Studio のプロジェクトの追加と、ビルド・実行の確認
4. 記事本文の執筆(`fujiwo-manuscript-voice`)
5. 既存の連載の記事の更新。書き終えた記事へのリンクを、すでにある連載の記事のリンクの一覧に足す(7節)
6. 検証(`執筆プロファイル.md` 6節、`python3 Tools/check_article_sources.py`、`python3 Tools/build_cpp_samples.py`)とレビュー(`review-manuscript-natural-japanese`。結果は `Reviews/` に置く)

4本を書き終えたら、4本を通して読み、用語(5節)と分担(3節)の重複・抜けがないかを確かめる。

## 7. 連載であることの示し方

8-1 の決定に基づき、各記事を次のように書く。

- 各記事は1本で読めるように書く。
- 冒頭の前提と、その直後の `※ MSVC で指定できる最も古い C++ の言語標準は C++14 (...)` の注記(既存の記事と同じ)の後に、連載名・何本目か・ほかの記事へのリンクを置く。
- リンクは、書き終えた記事にだけ張る。まだない記事は、書名もリンクも載せない(`執筆プロファイル.md` 2節の「予告は付けない」に沿う)。CI は `check_markdown.py` を `--fail-on-findings` 付きで実行するので、未執筆の記事へのリンクがあると失敗する。
- 新しい記事を書き終えるたびに、すでにある連載の記事のリンクの一覧に、その記事を足す(6節の手順 5)。
- 本文での予告(「次の記事で〜」)は書かない。
- 前の記事で説明した内容は、本文で要点を1〜2文で述べてから、リンクを添える。
- リンク先は同じフォルダーの記事なので、`執筆プロファイル.md` 4-3 のリンクの制限には触れない。
