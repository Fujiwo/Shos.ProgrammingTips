## 3. 指摘事項

優先度は、高 (動作や取り決めに反する)・中 (放置すると混乱を招く)・低 (改善の提案) の3段階で付けた。

### 3-1. リポジトリの構成

1. **高 — C++ のソリューション名が `CLAUDE.md` と違う**
   `CLAUDE.md` と `執筆プロファイル.md` 1節・4-1は、C++ のソリューションを `CPlusplusTips` と定めている。実体は `Articles/CPlusplus/Sources/CPlusplusTips/HelloCPlusplusTips.slnx` で、C# 側の `CSharpTips.slnx` とも命名がそろっていない。`CPlusplusTips.slnx` に改名するのがよい。

2. **高 — `HelloCPlusplusTips` プロジェクトにソースファイルがない**
   `HelloCPlusplusTips.vcxproj` には `ClCompile` の項目が一つもなく、`main.cpp` もない (ほかの2プロジェクトにはある)。ソリューション全体をビルドすると、このプロジェクトのリンクが失敗する可能性が高い (MSVC では未確認)。また、言語標準が `stdcpp23` で、ほかの2プロジェクト (`stdcpp14`) と違う。記事に対応しない雛形のプロジェクトなので、削除することを勧める。C# の `HelloCSharpTips` も同様に雛形であり、最初の C# の記事を書く時点で削除するか、残す理由を `CLAUDE.md` に書いておくとよい。

3. **中 — 使われていないバナー画像が残っている**
   `Articles/CPlusplus/Images/CPlusplus11-auto-banner.svg` は、どの記事からも参照されていない。`執筆プロファイル.md` 4-2は「記事の冒頭に、飾りのための画像 (バナー) は置かない」と定めており、方針変更前の残りと思われる。計画書 `Plans/CPlusplus11-auto.md` 1節の表にも「バナー画像 … (新規作成)」が残っている。画像を削除し、計画書の行は削除するか「(方針変更により不採用)」と注記する。

4. **中 — 中身が空のファイルが Git 管理下にある**
   `.claude/loop.md`、`Articles/CPlusplus/Sources/CPlusplusTips/.claude/launch.json`、`Articles/CPlusplus/Sources/CPlusplusTips/.mcp.json` の3つは0バイト。特に空の `.mcp.json` は JSON として不正なので、そのフォルダーで Claude Code を起動したときに設定の読み込みエラーになりうる。不要なら削除し、`.gitignore` に入れるかどうかも決めておく。

5. **中 — 目次の生成結果が、空フォルダーの有無で変わる**
   `update_articles_toc.py` の `language_directories()` は、`Articles/` の下に実在するフォルダーだけを列挙する。`Articles/JavaScript/` (と `Articles/CSharp/` の記事部分) は、手元では空のフォルダーとして存在するが、Git は空フォルダーを管理しない。現在の `Articles/JavaScript/Sources/JavaScriptTips/` は空で Git に入っておらず、新しくクローンした環境で `--force` を実行すると、目次から「## JavaScript」の節が消える。対策は次のどちらか。
   - スクリプトで、`LANGUAGES` に載っている言語は、フォルダーがなくても節を出す。
   - `JavaScriptTips/` に `.gitkeep` などを置いて、フォルダーを Git に入れる。

6. **低 — 作業ツリーの改行コードが `.gitattributes` とそろっていない**
   `.gitattributes` は `eol=lf` を指定しているが、作業ツリーでは `CPlusplus11Auto/main.cpp`・各 `.vcxproj`・`.slnx`・`.gitignore` などが CRLF になっている (インデックスは LF)。`.gitattributes` を追加する前にチェックアウトしたファイルが残っているためと思われる。同じフォルダーの `CPlusplus11Lambda/main.cpp` は LF で、エディターによっては差分が混乱する。コミット済みの状態で該当ファイルをチェックアウトし直すと、LF にそろう。

7. **低 — `Reviews/` のファイル名に規則がない**
   既存のファイルは `自然な日本語レビュー.md`・`自然な日本語レビュー20261024.md`・`自然な日本語レビュー20261024-2.md` で、日付の有無がまちまちで、どの記事のレビューかもファイル名から分からない。`<レビューの種類>-<対象>-<YYYYMMDD>.md` のような規則を `CLAUDE.md` の「フォルダーの使い方」に書いておくと、探しやすくなる。

8. **低 — リポジトリ直下に README とライセンスがない**
   GitHub で公開するなら、リポジトリの目的と `Articles/README.md` (目次) への入り口を書いた `README.md` と、記事・サンプルコードの利用条件 (`LICENSE`) を置くとよい。記事とコードでライセンスを分けるかどうかも決めておく。

### 3-3. フック (`.claude/hooks/`)

3本とも短く、入口 (`main`)・判定 (`is_..._edited`)・処理が分かれていて読みやすい。指摘は軽微なものだけ。

1. **低 — `update_articles_toc.py` の `read_title()` がコードブロックを区別しない**
   最初の `# ` で始まる行をタイトルとするので、H1 より前に、`# ` で始まる行を含むコードブロック (シェルのコメントなど) があると、それをタイトルにしてしまう。現在の記事はすべて1行目が H1 なので実害はない。フェンスの中を飛ばすか、「1行目が H1 でなければ警告する」程度の対策で足りる。

2. **低 — タイトル中の `[` `]` がエスケープされない**
   目次の行は `- [{タイトル}]({リンク})` で組み立てている。タイトルに `[` `]` を含む記事 (C++ の属性 `[[nodiscard]]` を扱う記事など) を書くと、目次のリンクが崩れる。`[` `]` を `\[` `\]` に置き換えておくとよい。

### 3-4. 記事

記事は2本とも、執筆プロファイルの主要な規則 (冒頭の「〜を紹介します」、言語の前提、`例 N. 「...」` の連番、半角括弧の前後の空白、数字の表記、ソースコードへのリンクを入れないこと) を満たしている。技術的な内容の誤りは見つからなかった。以下は、内容を補うための提案。

#### `CPlusplus11-auto.md`

1. **中 — 波括弧での初期化の落とし穴に触れていない**
   C++11 では、`auto x{1};` や `auto x = {1};` の型が `std::initializer_list<int>` になる。`auto x{1};` は C++17 (N3922) で `int` に変わったため、言語標準によって推論結果が違う。「使うときの注意点」で、C++11 の範囲の記事として触れておく価値がある。記事の冒頭で「C++11 以降」とし、MSVC では `/std:c++14` でビルドしているので、読者の環境によって結果が異なる点も注記するとよい。

2. **低 — C# の `var` との比較は、前提の知識を求める**
   62行目「C# の `var` と同じく静的型付けのままで」は、C# を知らない読者には補足にならない。C++ の記事として独立して読めるよう、比較を残すなら「(C# を知っている方向けには、`var` と同じです)」程度に弱めるか、なくても意味が通る。

#### `CPlusplus11-lambda.md`

1. **中 — `[=]` による `this` の暗黙のキャプチャーが C++20 で非推奨になったことに触れていない**
   キャプチャーの表 (130行目) と「使うときの注意点」(216行目) は C++11 の規則として正しい。ただし、C++20 では `[=]` による `this` の暗黙のキャプチャーが非推奨になり、`[=, this]` と書くことが求められる。新しい言語標準でビルドすると警告が出るので、`※ ` の注記で一言触れておくと、実務の読者に親切。

2. **低 — 比較表の「型名を書けるか: 書けない」は、少し強い**
   205行目。クロージャー型には名前がないが、`decltype` で型を得ることはできる。「名前がない (`decltype` で得ることはできる)」とするか、表の観点を「型に名前があるか」に変えると正確になる。

3. **低 — 分量が目安をやや超えている**
   本文は約3,550字で、目安 (2,000〜3,000字) を2割ほど超える。CLAUDE.md は増減を認めているので問題ではない。削るなら、「関数ポインター・関数オブジェクトとの比較」の表のあとの段落 (210行目) が「ラムダ式を使うメリット」の節と内容が重なるので、候補になる。
