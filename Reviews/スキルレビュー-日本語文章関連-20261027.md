# 日本語文章関連スキルのレビュー

レビュー日: 2026-10-27

入口スキルで読む順序と衝突時の裁定をまとめ、意味保持を独立して確認する設計は妥当です。ただし、同期元を逆に説明している箇所と、文章を改善しなくても診断スコアが上がる問題があります。先にこの2件を直し、その後で Windows の実行例と完了条件を整理することを勧めます。

指摘は5件です。優先度は、誤った運用や診断につながるものを P1、特定環境の実行失敗や手順の不整合を P2 としました。スキル・原稿・設定は変更していません。

## 対象と確認方法

正として管理されている [.claude/skills/](../.claude/skills/) の次の8スキルを対象にしました。

- [fujiwo-manuscript-voice](../.claude/skills/fujiwo-manuscript-voice/SKILL.md)
- [fujiwo-style](../.claude/skills/fujiwo-style/SKILL.md)
- [japanese-tech-writing](../.claude/skills/japanese-tech-writing/SKILL.md)
- [natural-japanese](../.claude/skills/natural-japanese/SKILL.md)
- [stop-ai-slop-jp](../.claude/skills/stop-ai-slop-jp/SKILL.md)
- [yomiyasu](../.claude/skills/yomiyasu/SKILL.md)
- [explain-before-shorten](../.claude/skills/explain-before-shorten/SKILL.md)
- [review-manuscript-natural-japanese](../.claude/skills/review-manuscript-natural-japanese/SKILL.md)

各スキルの本体に加え、入口の裁定表・チェックリスト・除外規則・導入ガイド・補助スキル統合手順、診断スコアの定義、関連する文書型とスクリプトを確認しました。[CLAUDE.md](../CLAUDE.md) と [執筆プロファイル.md](../執筆プロファイル.md) による上書きも考慮しています。補助資料とスクリプトの全行監査ではありません。

指示同士を照合し、実行可能性に関わる箇所は Python 3.13.14、Windows PowerShell 5.1.26100.9711、PowerShell 7.6.9 で確認しました。検証用の本文と JSON は一時領域だけに作成し、削除しました。対象8スキルについて、キャッシュを除く配下の実ファイルを同期先の [.github/skills/](../.github/skills/) とバイト比較し、不一致・欠落がないことも確認しています。

## 指摘

### 1. [P1] 導入ガイドが同期元と同期先を逆に説明している

根拠: [adoption-guide.md](../.claude/skills/fujiwo-manuscript-voice/references/adoption-guide.md) 27行。

導入ガイドには、配布元リポジトリでは `.github/` を正とし、`sync-copilot-to-claude` で `.claude/` に反映するとあります。実際は逆です。[CLAUDE.md](../CLAUDE.md) は `.claude/skills/` を正と定め、[sync_skills.py](../.claude/hooks/sync_skills.py) もその内容を `.github/skills/` にミラーリングします。

この説明を信じて同期先だけを編集すると、次の正規同期で変更を上書きされるおそれがあります。同期元にないファイルは削除されるため、新規追加も失われます。導入ガイド単体で利用するときに、指示ファイルとの不一致を見落としやすい点も問題です。

**改善案:** 配布元固有の同期方向とコマンド名を、汎用スキルの導入ガイドから外します。導入先で正と同期方向を明示し、プロジェクトの指示ファイルに従う説明にすれば、汎用性も保てます。

### 2. [P1] 診断対象から除いたコードが自然度スコアを押し上げる

根拠: [diagnose.md](../.claude/skills/natural-japanese/references/diagnose.md) 20・24行、[lint.py](../.claude/skills/natural-japanese/scripts/lint.py) 1714行付近。

診断では、指摘の重みを文書の文字数で割って減点します。文字数には Markdown 記法を含む全体の長さを使います。一方、通常の文章検査ではフェンス付きコードなどをマスクします。そのため、指摘を検出しない部分だけを増やしても、減点が小さくなります。

同梱の [ai-smelly.md](../.claude/skills/natural-japanese/scripts/fixtures/ai-smelly.md) に、ASCII のコードを繰り返した `cpp` のフェンス付きブロックを末尾追加して再現しました。本文は変えていません。

| 条件 | 文書の文字数 | critical / warn / info | 定義式による自然度 |
|---|---:|---|---:|
| 元の試料 | 1,813 | 5 / 6 / 14 | 60.84 |
| コードだけ追加 | 19,956 | 5 / 6 / 14 | 96.44 |

両者の指摘は、行番号・カテゴリ・重大度・抜粋まで一致しました。それでも、定義上の判定帯は「要修正」から「自然」に変わります。これは目視評価を含まない quick 診断の結果であり、実際の文章の自然さが改善したことを示しません。

このリポジトリはコードを含む技術記事を対象とするため、極端な試料だけの問題ではありません。同じ本文でも、コードの掲載量で診断が変わります。

**改善案:** 分母を、検査対象となった地の文の文字数に合わせます。マスク後の改行や空白だけで文字数が増えない定義も必要です。地の文が不足する場合は採点せず、診断不能とします。入口の [exclusions.md](../.claude/skills/fujiwo-manuscript-voice/references/exclusions.md) で除外した定型由来の指摘を、得点計算でも除くか明記してください。

### 3. [P2] Windows PowerShell 5.1 では記載どおりの baseline 検査が失敗する

根拠: [入口の SKILL.md](../.claude/skills/fujiwo-manuscript-voice/SKILL.md) 91行、[lint.py](../.claude/skills/natural-japanese/scripts/lint.py) 1891行。

PowerShell の例は、JSON を `Out-File -Encoding utf8` で保存します。Windows PowerShell 5.1 では、この指定により UTF-8 BOM が付きます。読み込み側は `encoding="utf-8"` で読んだ文字列を JSON として解析するため、BOM があると失敗します。

記載された文字コード設定とパイプ処理をそのまま使い、続けて `--baseline` を指定して確認しました。

- Windows PowerShell 5.1: lint の終了コードは 1。`Unexpected UTF-8 BOM` で失敗。
- PowerShell 7: lint の終了コードは 0。比較は成功。

`PYTHONUTF8=1` とコンソールの出力文字コード指定だけでは、保存ファイルの BOM は防げません。

**改善案:** PowerShell 7 以上を前提として明記するか、5.1 でも BOM なしで保存できる例にします。スクリプト側で BOM 付き UTF-8 を受け付ける方法もありますが、どちらを採るかを決め、保存から再読込までを検証する必要があります。

### 4. [P2] 「残す」指摘の存在が完了条件になっている

根拠: [入口の SKILL.md](../.claude/skills/fujiwo-manuscript-voice/SKILL.md) 109行、[裁定表](../.claude/skills/fujiwo-manuscript-voice/references/conflict-resolutions.md) の裁定10、[チェックリスト](../.claude/skills/fujiwo-manuscript-voice/references/manuscript-checklist.md) 120行。

台帳に「残す」の行を必ず残し、「直した」だけの台帳は不合格としています。しかし、指摘が0件の場合や、短い原稿で見つかった唯一の誤りを直した場合には、残すべき指摘がありません。

一律修正を防ぐ目的は理解できますが、残す指摘の件数では、修正が適切だったかを判断できません。この条件を満たそうとすると、不要な指摘を作るか、直せる問題を残すことになります。

**改善案:** 検出した指摘をすべて「直す／残す」に仕分けることと、変更しない部分を尊重することを完了条件にします。「残す」が0件でもよく、問題がない場合は「指摘なし」で完了できるようにしてください。

### 5. [P2] full モードでサブエージェントを使う条件が一致していない

根拠: [natural-japanese の SKILL.md](../.claude/skills/natural-japanese/SKILL.md) 22行、[入口の SKILL.md](../.claude/skills/fujiwo-manuscript-voice/SKILL.md) 57・101行。

工程の骨格である natural-japanese は、full で構造・読みやすさ・文書型照合を並列サブエージェントに「必ず」担当させるとしています。入口はモードの使い分けを同スキルに従わせる一方、自身の検査工程では full でサブエージェントに「分けてよい」としています。

同じ full 指定でも、必須工程と解釈するか、任意の実行方法と解釈するかで、実行内容とコストが変わります。[診断モードの定義](../.claude/skills/natural-japanese/references/diagnose.md) は、通常モードより自分を優先すると明記していますが、入口側にはこの相違について同等の裁定がありません。

**改善案:** 必須なのは三つの観点の確認とし、担当を分けるかどうかは文量・独立性・実行環境に応じて選ぶ形を勧めます。入口が通常モードを上書きするなら、その範囲を明記してください。サブエージェントを利用できない環境で、どこまで確認したら full 相当とするかも定めると明確です。

## 設計上の改善候補

次の2点は、上の再現可能な不具合とは分けて扱います。

### 必読資料を、常時必要な規則と症状別の資料に分ける

[入口の読む順序](../.claude/skills/fujiwo-manuscript-voice/SKILL.md) は、quick でも複数スキルの全文と裁定表などを読み込ませます。特に [yomiyasu の本体](../.claude/skills/yomiyasu/SKILL.md) だけで約2.2万字あり、文末と意味保持に関する説明が複数の工程で繰り返されています。

読み漏らしを防ぐ設計ですが、小さな修正にも同じ準備が必要です。quick は必須読込まで含めた深さなのか、検査工程だけの深さなのかを明示するとよいでしょう。共通原則と裁定は必読にし、文末・係り受け・報告文などの詳細は、症状に応じて参照する構成を検討できます。

### 「イ形容詞＋です」は、一律の破綻判定ではなく文脈で判断する

[japanese-tech-writing](../.claude/skills/japanese-tech-writing/SKILL.md) 73行と [fujiwo-style](../.claude/skills/fujiwo-style/SKILL.md) 83行は、「難しいです」などを前後の流れが切れている兆候として書き直させます。

例えば「この設定では初回の処理が遅いです。二回目以降はキャッシュを使います。」は、条件と処理の違いを普通に説明できます。文末の形だけでは、流れが破綻しているとは判断できません。前後の文を結合すると、かえって条件の掛かる範囲を追いにくくする場合もあります。

著者の表現上の好みとして避ける方針はあり得ます。ただし、その場合は文法や文章一般の問題とせず、著者指定として区別することを勧めます。一般的な規範は、孤立した文や論理関係の不明確さが実際にあるかを見る形にすると、意味保持の原則とも合わせやすくなります。

## 維持したい設計

- **プロジェクト固有の規則を分離していること。** [執筆プロファイル](../執筆プロファイル.md) を上位に置くため、実務経験者向けの記事に、学習者向けの用語説明や書籍の章間接続を一律に追加せずに済みます。
- **意味保持を四つの観点で確認していること。** [yomiyasu の統合手順](../.claude/skills/fujiwo-manuscript-voice/references/yomiyasu-integration.md) は、主張・比重・言い切りの強さ・文の働きを比べます。警告が消えたことを意味の等価性と取り違えない点も適切です。
- **説明の組み立て直しを限定していること。** [explain-before-shorten](../.claude/skills/explain-before-shorten/SKILL.md) は、口語化と口頭での内容整理を区別しています。入口でも、症状がある段落だけに使い、未知の条件を足さないよう裁定しています。
- **単独スキルの衝突を入口で処理していること。** 見出し、断定と推量、太字、カタカナ語、自称などの相違は、既に [裁定表](../.claude/skills/fujiwo-manuscript-voice/references/conflict-resolutions.md) で処理されています。単独ファイル同士の差だけを理由に、未解決の問題とは数えていません。
- **記事全体レビューの対象を明示していること。** [review-manuscript-natural-japanese](../.claude/skills/review-manuscript-natural-japanese/SKILL.md) は、通常の audit より広いチェックを行い、原稿横断の用語の不整合も確認します。本文を変更しない制約も明確です。

## 修正順序と回帰確認

1. 同期方向の誤記を除き、編集先を誤らない状態にする。
2. 診断スコアの分母と採点可能条件を直す。
3. PowerShell の保存例と baseline 読み込みを整合させる。
4. 「残す」指摘の件数によらない完了条件にする。
5. full モードの必須観点と実行方法を分ける。

修正後は、少なくとも次を回帰確認してください。

| 確認対象 | 期待する結果 |
|---|---|
| 同じ本文にコード・引用・表だけを追加 | 地の文の診断スコアが不当に改善しない |
| 地の文がない、または不足する文書 | 高得点ではなく採点不能になる |
| プロファイルで除外する定型の反復 | 採点と所見で除外の扱いが一致する |
| PS5.1 と PS7 で JSON 保存後に baseline 比較 | 対応環境では成功し、非対応なら前提が明記される |
| 指摘0件、または唯一の指摘を修正済み | 「残す」項目を作らずに完了できる |
| full を入口経由と単独で実行 | 必須の確認観点と、委譲する条件を説明できる |

今回確認したのは、指示の整合性と一部のスクリプト動作です。複数モデルによる改稿品質の比較、診断スコアと人の評価の相関、所要時間の妥当性は検証していません。`exp` のモデルダウンロードや原稿の改稿も行っていません。
