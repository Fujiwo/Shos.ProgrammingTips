## 指摘

### 1. [P2] 箇条書き主体の文書が、full でも採点できなくなった

根拠: [diagnose.md](../.claude/skills/natural-japanese/references/diagnose.md) 28行、[textcore.py](../.claude/skills/natural-japanese/scripts/textcore.py) の `mask_markdown_structure`。

`prose_char_count` は、見出し・箇条書き・表をマスクした後の文字数です。そのため、箇条書きだけで書いたスライド構成案や議事録では0になります。見出しと箇条書きだけの16行の試料で確かめると、`prose_char_count` は0、finding も0件でした。diagnose.md の規定では、この文書は「診断対象の地の文が短すぎる」として採点されません。

natural-japanese は議事録やスライド構成案も対象にしており、SKILL.md §4 は「箇条書き主体の議事録・スライドでは lint がほぼ素通りするため、構造レビューが主役になる」と書いています。ところが、構造レビューの所見を反映する判断調整は、機械ベースの点数がないと使えません。full で構造を確かめても、点数を返せない状態です。

前回の修正前は、このような文書は減点0で100点になっていました。根拠のない満点を返すよりは採点不能のほうが正直です。ただし、この結果を意図したものかどうかが文書に書かれていません。

**改善案:** 次のどちらかを明記します。

- 箇条書き主体の文書は score の対象外とし、構造レビューの所見だけを返す。
- full / exp では、構造レビューを基にした点数を別の式で出す。その場合は、機械ベースがないことを内訳に書く。

このリポジトリの記事は地の文が1,800字前後あるので、記事の診断には影響しません。

### 2. [P2] 追加した回帰テストが CI で実行されない

根拠: [natural-japanese の SKILL.md](../.claude/skills/natural-japanese/SKILL.md) 89〜93行、[check.yml](../.github/workflows/check.yml)。

`test_lint.py` は、前回の指摘2・3の再発を防ぐテストです。しかし実行の手がかりは「lint を変更した場合は実行する」という SKILL.md の一文だけで、CI のジョブには含まれていません。CLAUDE.md が想定するエディターや Git 操作による編集では、テストを実行しないまま push される可能性があります。

また、テストは `lint.run_lint` を読み込むので、sudachipy と sudachidict-core が必要です。`lint.py` は `uv run` のインラインの依存指定で動きますが、記載の `python -m unittest` ではこの指定が効きません。依存を入れていない環境では、テストが失敗します。記載例が PowerShell の形(`\` 区切り)だけである点も、入口スキルが bash と PowerShell の両方を載せているのと揃っていません。

**改善案:** check.yml に、sudachipy と sudachidict-core を入れてテストを実行するステップを足します(CI はリポジトリ側の設定なので、スキルの汎用性には影響しません)。SKILL.md には、依存の導入方法と bash の例を足します。

### 3. [P3] natural-japanese §4 の見出しが「二つのレビュー」のまま

根拠: [natural-japanese の SKILL.md](../.claude/skills/natural-japanese/SKILL.md) 97行。

前回の指摘5の反映で、実行モードの節・diagnose.md・入口スキルは「構造レビュー・読みやすさレビュー・doctype照合」の三観点を必須としました。一方、§4 の見出しは「判断台帳と二つのレビュー」のままで、doctype 照合は構造レビューの中の一文にとどまっています。三観点を確かめるとき、doctype 照合を独立した観点として読み落とすおそれがあります。

**改善案:** 見出しを三観点に合わせるか、doctype 照合を独立した小見出しにします。

### 4. [P3] 全文レビュースキルが、入口スキルの読む順序を古い形で書いている

根拠: [review-manuscript-natural-japanese の SKILL.md](../.claude/skills/review-manuscript-natural-japanese/SKILL.md) 20行。

「そこが固定する順序(fujiwo-style → japanese-tech-writing → natural-japanese → stop-ai-slop-jp)」とあり、補助スキルの yomiyasu と explain-before-shorten が入っていません。入口スキルの1節は、この2スキルを読む条件まで定めています。全文レビューは書き換えをしないので実害は小さいものの、チェックリストの4節(説明の組み立て、局所的な読みやすさ)はこの2スキルに基づいています。

**改善案:** 順序を列挙せず、「入口スキルの1節が定める順序と読込範囲に従う」と参照する形にします。入口を直すたびに、こちらを直さずに済みます。

### 5. [P3] yomiyasu_diff が、変更のない本文でもつながりの候補を出す

根拠: [yomiyasu_diff.py](../.claude/skills/yomiyasu/scripts/yomiyasu_diff.py) 97・771行。

同じファイルを修正前・修正後として渡しても、`logic` に8〜13件の候補が出ました(`Articles/CPlusplus/` の4記事)。候補には次のものが含まれます。

- 見出しの「これまでの書き方と課題」。見出しが文として扱われている。
- 「これまで」で始まる文。正規表現 `^(?:これ|…)` が、指示語ではない「これまで」にも一致する。

`logic` は、書き直した文のうち、つながりを確かめる場所を示す設計です。ただ、比較対象は本文全体なので、変更していない文も毎回並びます。[yomiyasu-integration.md](../.claude/skills/fujiwo-manuscript-voice/references/yomiyasu-integration.md) 3節は「候補を目視で確認」するよう求めているため、記事1本ごとに確認の手間が増えます。

**改善案:** 見出し行を対象から外し、「これまで」「これから」などを指示語の判定から除きます。あわせて、`logic` を変更のあった文に限るオプションを検討してください。

## 文言の小さな不整合

指摘とは分けますが、前回の反映で次の2か所の文がぎこちなくなっています。

- [fujiwo-style](../.claude/skills/fujiwo-style/SKILL.md) 83行は、「敬体基調で避けること」という項目の中に「イ形容詞＋です」を「残す」規定を置いています。避けることの列挙として読むと、意図が伝わりにくい位置です。
- [japanese-tech-writing](../.claude/skills/japanese-tech-writing/SKILL.md) 73行は「イ形容詞に『です』を続けた文(…)も」と「も」で始まりますが、直前の項目は別の話題で、「も」の受け先がありません。

## 維持したい設計

- **採点の分母を lint の出力に固定したこと。** 分母の計算を人やモデルの判断に任せず、`stats.prose_char_count` という一つの値にしたので、除外の扱いと採点の再現性が揃いました。
- **反映を3か所で揃えたこと。** 完了条件と full の扱いは、入口・裁定表・チェックリスト(または natural-japanese・diagnose.md)で同じ言い方になっており、どれを先に読んでも同じ結論になります。
- **相互参照が実在すること。** 入口スキルが名前で参照する節は、確認した範囲ではすべて実在しました。

## 修正順序

1. 箇条書き主体の文書の採点の扱いを決め、diagnose.md に書く。
2. check.yml にテストのステップを足し、SKILL.md にテストの依存と bash の例を書く。
3. §4 の見出しと全文レビュースキルの記述を、入口スキルに揃える。
4. yomiyasu_diff の候補の絞り込みを検討する。

今回確認したのは、前回の反映、相互参照、スクリプトの動作です。改稿の品質や、診断スコアと人の評価の相関は検証していません。
